# continuous_fg_ins

Continuous Time INS Factor graph based on Cubic Basis Splines. This is my attempt at using GTSAM develop banches new CUDA capability to estimate parameters for a Cubic Basis Spline around a closed circuit using an IMU and multipl Novatek Pwr-Pak 7D receivers as aiding sources. Much of this work will be based off of a recent ION Navigation Journal: [Spline-Based Factor Graph Estimation with High-Grade Inertial Sensors](https://navi.ion.org/content/73/1/navi.742). This paper gives a formulation for how to parameterize a vehicle's trajectory as a set of Cubic Basis Splines (Cubic B Splines) parameterized by a set of **Control Points**. I will define what these control points are in following sections. This formulation has several advantages over discrete-time state estimation techniques. Primarily, by describing the problem in continuous time, we are allowed to apply constraints at an arbitrary point in time. This helps alleviate some of the need for systems like PTP timing synchronization to enable multi-sensor fusion into a single navigator. 

# Cubic Basis Splines

When doing factor graph based navigation systems, especially systems that use an IMU as a motion model, you have to solve the problem of keeping the graph from becoming massive very quickly. As a thought experiment, if an IMU runs at 100 Hz, every measurement adds a new constraint and so over 1 second you add 100 nodes. If you are estimating a PVA state with IMU biases, then you have to add a decision vector containing pos, vel, att, biases every $100^{	ext{th}}$ of a second. This quickly becomes unreasonable to solve. Discrete factor graphs solve this with techniques like *IMU Pre-Integration*, where IMU measurements are "lumped" together between a set of nodes into one motion constraint that is independent of the state at each of the connecting nodes. This works if you have only one set of measurements to generate the pre-integration constraint between. For example if we have 10 Hz GNSS, the graph grows at a rate of 10 Hz and not 100 Hz. However, this becomes problematic if we have multiple "fixing" measurements like GNSS, Camera, and LiDAR, all at different rates. If they are not tied to a common clock with something like PTP then it is more difficult to add nodes in a cohesive manner while keeping graph size tractable. This is where *Cubic Basis Splines* come in!

## Standard vs Cumulative Basis Splines

There is apparently a difference between "Standard" and "Cumulative" Cubic basis splines. Standard basis splines seem to work better for translation splines (Cartesian vehicle pos/vel/accel) whereas Cumulative basis splines seem necessary for attitude splines. This has something to do with how standard splines don't restrict movement. This allows the estimate of position to go any which way which is more representative of real world vehicle translation. I don't know why the same argument cannot apply to attitude (i.e. a vehicle can also rotate basically any which way). My reading seems to indicate that it has something to do with how the spline actually computes attitude requires the cumulative spline due to the spline existing on $SO(3)$ not in $\mathbb{R}^3$. As I do not feel I currently understand where to use Standard and where to use Cumulative Basis Splines, I will present how to use both. That is what Vio Slam currently is working towards and so it is what I put here.
